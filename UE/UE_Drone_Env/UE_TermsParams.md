# UE_TermsParams.md

A small dictionary of Unreal Engine (UE) terms, file prefixes, and “how UE thinks” concepts used in this repo.

---

## Core UE concepts

**Project**  
A UE project folder containing `Config/`, `Content/`, `Plugins/`, and (optionally) `Source/`. The `.uproject` file is the project entrypoint.

**Content (asset space)**  
`Content/` is where UE-managed assets live (Blueprints, meshes, materials, maps). Assets here show up in the Content Browser and can be cooked/packaged.

**Asset**  
A UE-managed object stored as a `.uasset` (and sometimes `.umap`). Blueprints, Materials, Meshes, DataAssets, Interfaces are all assets.

**Actor**  
A “thing that can exist in the world.” Can be placed in a level or spawned at runtime.

**Pawn**  
A controllable Actor. Often possessed by a PlayerController or driven by AI/external control.

**Character**  
A Pawn specialized for humanoid/walking movement (capsule + CharacterMovement). Usually *not* ideal for true 6DOF drone flight.

**Component**  
A modular capability attached to an Actor/Pawn (mesh, camera, movement, sensors). Components are how UE encourages composition.

**ActorComponent**  
A logic component (no transform). Used for reusable modules like movement logic, telemetry sampling, etc.

**SceneComponent**  
A component with a transform (location/rotation/scale). Used for mounts and sensor rig points.

**StaticMeshComponent**  
A SceneComponent that renders a Static Mesh (geometry).

**CameraComponent**  
A view definition (POV). Has properties like FOV. Does *not* inherently export images by itself.

**SceneCaptureComponent2D**  
A “render-to-texture camera.” Renders the scene into a `TextureRenderTarget2D` when triggered (on-demand or every frame).

**TextureRenderTarget2D**  
The texture buffer that SceneCapture writes into (resolution, format). Often the source for PNG export or streaming.

**GameMode / PlayerController**  
Framework classes controlling game rules and player possession. In this repo, these are typically minimal.

## Interfaces vs Data vs Logic

**Blueprint Interface (BPI_)**  
A contract: “any Actor implementing this must provide these functions.”  
Used to decouple systems (SampleManager queries drones without hard casting).

**DataAsset (DA_)**  
A UE asset that stores configuration data (inert).  
It does *not* execute logic. Runtime objects copy DA defaults into variables and can override in memory.

**User Defined Struct (ST_)**  
A typed schema for structured data (e.g., `ST_RunConfig`). Useful for clean parsing/mapping of config payloads.

## Key IO terms (this repo’s mental model)

**RunConfig / SET_CONFIG**  
A configuration payload generated by tooling (from YAML) and injected into UE at runtime (typically as JSON).  
Fail-fast design: UE refuses to run until config is accepted and ACKed.

**Runtime Override**  
Config stored in memory that overrides defaults for the duration of the run (movement tuning, sensor rig parameters, telemetry selection, capture settings).

**Infrance vs Controller**  
- **Infrance** = data out (pose/viewpoints/telemetry). Read-only contract via BPI.  
- **Controller** = commands in (move/capture/spawn). Writes/acts on the sim.

**Capture / Snapshot**  
An “atomic” sampling moment: one `capture_id` ties together pose + telemetry + viewpoint + image(s) and the config_id/hash used.

## Common UE “spaces” and transforms

**World Space**  
Coordinates in the global level.

**Local/Actor Space**  
Coordinates relative to the Actor’s transform.

**Component Space**  
Coordinates relative to a component’s parent.

**Forward/Right/Up vectors**  
Directional basis vectors derived from rotation. For drones, always be explicit about which space you mean.

## WebSockets (how comms works here)

**WebSocket**  
Bidirectional message pipe. UE the client (via plugin component). UE_Tooling/WebSocket is the server.

**Message envelope (protocol)**  
JSON object with at least: `type`, `run_id`, `drone_id`, `schema_version`, `seq/timestamp`, `payload`.  
Message types commonly used: `SET_CONFIG`, `CMD`, `CAPTURE_NOW`, `OBS`, `ACK`, `ERROR`.
Notes Above are not set in stone reson with human developer about truly required feilds. 

**Why protocol.py exists (tooling)**  
So every script uses one shared message shape and doesn’t drift.

## File/asset prefix glossary (conventions)

**BP_** — Blueprint Class (Actor/Pawn/Component Blueprint)  
Examples: `BP_DronePawn`, `BP_SampleManager`

**BPI_** — Blueprint Interface  
Examples: `BPI_DronePoseProvider`

**SM_** — Static Mesh  
Examples: `SM_DroneBody`, `SM_Sphere_1m`

**M_** — Material (shader)  
Examples: `M_Red_Solid`, `M_DroneBody_Base`

**MI_** — Material Instance 
Examples: `MI_DroneBody_Default`

**DA_** — Data Asset (config/data container)  
Examples: `DA_DroneMovementDefault`

**DT_** — Data Table (rows of structured data)  
Examples: `DT_SwarmSpawnTable`

**ST_** — User Defined Struct (typed schema)  
Examples: `ST_RunConfig`

**L_** — Level/Map (often used naming convention)  
Examples: `L_Sim`

## Practical “gotchas” worth remembering

**Blueprint assets must live under a mounted content root**  
Project `Content/` or Plugin `Content/`. Moving `.uasset` files outside those roots breaks discovery/cooking.

**CameraComponent ≠ image capture**  
For images you need SceneCaptureComponent2D + RenderTarget.

**Avoid per-drone sockets**  
Use one (or two) connections and route by `drone_id` in messages.

**Fail-fast config is cleanest for experiments**  
Gate spawning/control/capture until `SET_CONFIG` is accepted and ACKed.
