# Path_Optimizer — Dev README (Targets/Course Model Refactor)

This document is the detailed development guideline for refactoring `Path_Optimizer` to ingest the **official Unreal course-target export format**:

- `Path_Optimizer/course_model/targets-*.json`
- Example: `Path_Optimizer/course_model/targets-SimBlank-20260216_194648.json`

The goal is to adopt this format end-to-end (loader → internal data model → calculations → UI selection/visualization), while keeping the system deterministic and easy to extend.

---

## Decisions / requirements (from product direction)

1) **Refactor `load_scenario`** to support the `targets[]` schema **including axis orientation** (`axis_x/axis_y/axis_z`).

2) **Ordering logic must remain flexible**, but for now:
- **Use the order as listed in the JSON file** (no sorting by `Course_XX` yet).

3) **Simple unit conversion**:
- Inputs are Unreal `cm` (as exported); internal computations use meters.

4) **Axis orientation is required now**, but:
- We do **not** enforce a “required heading direction” yet.
- We may introduce a **minimal deterministic directionality rule** (temporary) and keep it clearly marked/commented.

5) **UI selection**:
- User selects a course by the **JSON filename**.

6) **Tests**:
- Add tests that validate parsing, ordering, and conversion.

---

## Official input schema (targets export)

Top-level example fields:

```json
{
  "name": "targets-SimBlank-20260216_194648",
  "level": "/Game/SimBlank/Levels/SimBlank",
  "mesh": "/Game/AutoGenerated/RedSphere/SM_Torus_1mOpening",
  "frame": "unreal",
  "units": "cm",
  "generated_at": "2026-02-16T19:46:48",
  "targets": [
    {
      "actor_label": "RedSphere_1m_Course_01",
      "actor_path": "...",
      "position_cm": {"x": 0, "y": 0, "z": 0},
      "axis_x": {"x": 1, "y": 0, "z": 0},
      "axis_y": {"x": 0, "y": 1, "z": 0},
      "axis_z": {"x": 0, "y": 0, "z": 1}
    }
  ]
}
```

Notes:
- The file can include a special `Origin` target (we will **treat it as just another target** for now since ordering is “as listed”).
- The `axis_*` vectors represent a target-local coordinate frame in world coordinates (typically orthonormal if exported from an Unreal transform).

---

## How this differs from the current point-based scenario format

Current `Path_Optimizer/data/scenarios/*.json` format is **point-only**:

```json
{"name":"...", "frame":"unreal", "units":"cm", "waypoints":[{"x":..,"y":..,"z":..}, ...]}
```

Official targets format differs by:
- Uses `targets[]` instead of `waypoints[]`.
- Position is nested (`position_cm.x/y/z`) instead of flat `x/y/z`.
- Includes actor identity (`actor_label`, `actor_path`).
- Includes full **orientation** (`axis_x/axis_y/axis_z`) per target.
- Includes metadata (`level`, `mesh`, `generated_at`).

## Refactor plan (end-to-end)

### A) Data model changes (`src/opt_engine/types.py`)

Add a target representation that preserves axis orientation:

- `TargetAxis` (or reuse a simple `{x,y,z}` dataclass)
- `Target`:
  - `actor_label: str`
  - `actor_path: str`
  - `position: Waypoint` (in scenario units/frame)
  - `axis_x/axis_y/axis_z: np.ndarray` (shape `(3,)`, float)

Update `Scenario` to carry targets + metadata:
- `targets: tuple[Target, ...] | None`
- `level: str | None`
- `mesh: str | None`
- `generated_at: str | None`

Compatibility strategy:
- Keep `Scenario.waypoints` as the canonical ordered positions used by the optimizer (so existing optimization code stays stable).
- When loading a `targets[]` file, populate:
  - `Scenario.targets` (full fidelity)
  - `Scenario.waypoints` (positions extracted from targets, **same order as listed**)

### B) Loader refactor (`src/opt_engine/scenario_io.py`)

Re-instrument `load_scenario()` to accept **either** schema:

1) If JSON contains `targets`:
   - Parse top-level fields (`name/frame/units/level/mesh/generated_at`)
   - Parse `targets[]` in file order
   - Extract positions from `position_cm`
     - keep `Scenario.units="cm"` and `Scenario.frame="unreal"` as declared
   - Parse axis vectors (`axis_x/y/z`)
   - Validate:
     - at least 2 targets
     - no consecutive duplicate positions
     - axis vectors are finite numbers
     - (optional warning) axis vectors near-unit + near-orthogonal
2) Else fall back to existing `waypoints` loader.

Implementation detail:
- Keep `list_scenarios()` but introduce a second listing function for course-model files, e.g.:
  - `list_course_models(course_model_dir: Path) -> list[Path]`
  - (or modify UI discovery to point at `course_model/` directly)

### C) Units conversion (`src/opt_engine/coords_unreal.py`)

We already convert `cm → m` for waypoint positions. Extend the same conversion concept to any orientation visualization scale (not the axis vectors themselves).

Axis vectors are unitless directions; do **not** scale them.

### D) Minimal deterministic “directionality” placeholder (not a constraint yet)

We need a deterministic rule for the direction “through” a target, but we are not enforcing it yet.

Proposed temporary rule (documented + clearly marked as provisional):
- Assume `axis_x` is the “forward/through” axis of the target.
- For a target `i`, define a direction vector:
  - `dir = axis_x`
  - If there is a “next” target, compute `delta = p_next - p_i`
  - If `dot(dir, delta) < 0`, flip: `dir = -dir`

This yields deterministic directionality consistent with the current ordering, without requiring any new constraints.

**Important:** keep this logic isolated (e.g., `opt_engine/targets.py`) and mark it as a placeholder pending confirmation of which axis corresponds to the target’s intended “through” direction.

### E) UI adoption (Dash)

Update the UI to select official targets files by filename:

1) Discovery (`app/dash_app.py`):
   - Point the dropdown to `Path_Optimizer/course_model/*.json`
   - Label options with the filename stem (e.g., `targets-SimBlank-...`)

2) Rendering:
   - Waypoints: plot target positions as markers, labeled by `actor_label` (or index if labels are too long).
   - Orientation: add an optional display toggle:
     - draw an axis triad per target (x=red, y=green, z=blue)
     - optionally draw the provisional “through direction” arrow

3) Optimizer integration:
   - Optimization continues to operate on the ordered positions (from targets).
   - Orientation is carried along for visualization and future constraints, but does not change the path calculation yet.

### F) Artifacts

Extend headless export (`run_optimize.py`) to include:
- a copy of the parsed `targets` metadata (labels/paths) when present
- optional: exported orientation vectors per target

### G) Tests (`tests/`)

Add tests that validate:
- `load_scenario()` can parse the `targets[]` schema
- order is preserved (“as listed”)
- unit conversion works (cm → m) when passed through coordinate conversion
- axis vectors are present and have correct shape

Recommended tests:
- `test_course_model_loader_parses_targets()`
- `test_course_model_preserves_order()`
- `test_course_model_cm_to_m_conversion()`

## Acceptance criteria for this refactor

- UI dropdown lists `Path_Optimizer/course_model/*.json` by filename.
- Selecting a targets file:
  - plots the target positions in the order provided by `targets[]`
  - (optional toggle) shows per-target axis orientation triads
  - optimization runs on the extracted positions without errors
- Tests pass in CI/local:
  - `PYTHONPATH=Path_Optimizer/src python3 -m pytest -q Path_Optimizer/tests`

## Open questions (track explicitly)

1) **Origin semantics**: should `Origin` be included in the optimized route, or ignored/prepended?
2) **Axis meaning**: which `axis_*` corresponds to “through the hoop” direction for your mesh (`axis_x` vs `axis_z`)? (We can keep the provisional rule until confirmed.)
3) **Axis quality**: should we re-orthonormalize the axes on load (e.g., via Gram–Schmidt) or trust the exporter?
4) **Future ordering strategy**: do we eventually want an ordering mode like `Course_01..Course_N` instead of “as listed”?
